# 交付与数据库初始化（组员先看这里）

## 1. 压缩包包含什么

- Django 项目源码、模板、静态资源、已有迁移、测试、任务书与 README。
- 独立入口 `init_database.py`，放在项目根目录，与 `manage.py` 同级。
- **不包含作者电脑的 MySQL 实时数据库、数据库导出、用户上传头像或本机凭据。**
- 不包含虚拟环境、PyCharm 本机配置、日志、审计报告、账号 CSV 和临时测试目录。
- 代码里的测试默认口令按课堂需求保留，没有修改作者既有密码。仅限受控演示环境。

不要把“建表成功”理解为“拿到了作者保存的数据”：`127.0.0.1` 指的是你自己的电脑。新建库只有执行演示选项后才有样例。

## 2. 从零运行（Windows PowerShell）

安装 Python 3.12 和 MySQL 8.0，确保 MySQL 服务正在运行。解压后进入有 `manage.py` 的项目目录。

```powershell
Set-Location "你解压后的项目目录"
py -3.12 -m venv .venv-hrms
$python = (Resolve-Path .\.venv-hrms\Scripts\python.exe).Path
& $python -m pip install -r requirements.txt

$env:DJANGO_DEBUG = "1"
$env:DJANGO_ALLOWED_HOSTS = "127.0.0.1,localhost"
$env:DJANGO_DB_HOST = "127.0.0.1"
$env:DJANGO_DB_PORT = "3306"
$env:DJANGO_DB_USER = "root"
$env:DJANGO_DB_PASSWORD = "填写你自己电脑的MySQL口令"

# 推荐：创建库/表、11名演示员工、6个账号、33条演示工资
& $python init_database.py --with-demo --with-demo-managers
# 上一步成功后再启动；报错先解决，不能忽略错误。
& $python manage.py runserver 127.0.0.1:8000
```

若没安装 Windows 的 `py` 启动器，使用本机 Python 3.12 可执行文件完成建环境这一步。变量仅在当前终端有效。项目不会自动读取 `.env`；新开终端需要重新配置。

浏览器访问 [本机系统](http://127.0.0.1:8000/)。详细代码讲解见 [README](../README.md)。

## 3. 按需要选择初始化方式

| 命令 | 行为 |
| --- | --- |
| `python init_database.py` | 仅建库、应用现有迁移、核对表/列，不创建业务账号 |
| `python init_database.py --with-demo` | 另外补齐基础样例：8员工、3账号、24工资（全新库） |
| `python init_database.py --with-demo --with-demo-managers` | 另外补齐熊大/熊二/光头强的测试档案、管理账号与工资（全新库共11员工、6账号、33工资） |

基础账号：admin、张三、王五；完整演示再加熊大、熊二、光头强。全新演示账号默认口令 `123456`，登录仍需要验证码。你已经存在的密码不会重置。

完整演示经理的初始口令也可以通过 `HRMS_DEMO_MANAGER_INITIAL_PASSWORD` 环境变量显式指定；这是新建账号的初始值，不会修改已有账号。

演示月份固定为 2025-01～2025-03：三个经理各有 3 条工资，实发 8500/8700/8900。展示薪资时请选择这些月份，当前月份没有样例是正常情况。其他实际工资应通过薪资管理按真实金额录入。

## 4. 怎样保证表结构一致

本脚本不手写另一套 `CREATE TABLE`，而是执行项目现有 Django 迁移：

1. 从同一份 `settings.py` 读取 MySQL 地址、库名、账户、口令。
2. 新库使用 utf8mb4；已有库不删除、不更改密码或默认字符集。
3. 检查 Django 配置、模型与迁移是否同步，再执行 `migrate`。
4. 检查没有未应用迁移，并核对模型需要的表和列，包括多对多关系表。
5. 同一个数据库的两个本脚本实例通过 MySQL 命名锁串行执行。

因此，组员解压**同一版本的完整项目**后建表，表结构由同一套迁移产生；不要只发送这个 py 文件、不要删除 migrations，也不要初次安装时自己执行 `makemigrations` 生成另一套迁移。

这不是任意损坏数据库的自动修复工具：它不能证明手工改动过的索引、字段类型或业务记录全部正确。已有表但没有迁移历史、库不是 utf8mb4、模型与迁移不同步或缺表/缺列时会停止，不使用 fake 迁移蒙混通过。MySQL 的部分 DDL 不能回滚，失败后请先备份/核对状态，不要直接清库。

首次建库需要 MySQL 用户有 CREATE DATABASE 权限；若管理员已建好库，脚本不再执行建库语句，但应用迁移仍需对应建表/改表及读写权限。脚本不依赖 mysql 命令行程序。

## 5. 人数与工资核对

完整演示的 admin 应看到：技术部 4 人、市场部 4 人、人力资源部 3 人，总计 11 人。人数图下有可见成员姓名，包括三个经理。部门管理员只显示负责部门，不能因此误判其他部门漏统计。

人数按员工档案统计，不按登录账号数量统计；没有登录账号的员工仍计入人数。全新演示有 11 人但只有 6 个账号，是正常设计。

如果另外创建了测试员工，可先预演，再补齐演示工资：

```powershell
& $python manage.py fill_demo_salaries --json
& $python manage.py fill_demo_salaries --apply --allow-demo
```

只给 `is_demo=True` 的档案生成虚构样例，已有工资保持不变，入职前月份跳过；不会自动为真实员工编造工资。重复运行不会新增重复工资。

## 7. 新增员工与账号管理

新建员工页面在具备账号开通权限时，默认勾选“同时开通登录账号”。须填写并确认初始密码；登录名留空默认使用员工姓名。登录名重复时可选择未占用的登录名；注册姓名重复时不能开通第二个账号，需核查原有身份。更换登录名不能绕过姓名检查，不会接管旧账号。新账号固定为普通员工，员工与账号保存失败时一起回滚。

没有账号开通权限的部门管理员只新增本部门档案，页面会禁用该选项并说明原因。取消勾选后只创建档案，列表提示“未开通登录账号”。既有账号和密码保持不变；新密码仍遵循系统原有验证规则。

系统用户列表默认按实际权限高低排序，而不是按创建顺序或角色名字。排序在分页前完成，共享权限去重；同权限层级、同权限数量按 ID 稳定排序。员工管理仍按职位的领导优先规则排序，两种排序不要混淆。

新账号的登录名、注册姓名不能重名，业务注册页和 Django 后台都复用服务端去重检查。既有账号姓名为空时会核对关联员工姓名；只有登录名的历史账号也不会被当作不存在。既有数据不批量改名或删除。员工档案和账号仍分离：不开户时可登记实际同名员工。
